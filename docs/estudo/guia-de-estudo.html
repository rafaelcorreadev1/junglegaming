O desafio em um parágrafo

Um serviço que movimenta carteiras de jogadores a partir de operações enviadas por provedores de jogos: aposta (BET), ganho (WIN), perda (LOSS), devolução (REFUND) e estorno (ROLLBACK). As operações chegam por HTTP e por fila (SQS), e o resultado financeiro precisa ser o mesmo nos dois caminhos, mesmo com várias instâncias rodando e com falhas no meio do processamento.

Spec 01

Bootstrap: módulo Go, Fx, config e Docker Compose

Um processo Go que sobe, valida a configuração, conecta no Postgres e responde dois endpoints de saúde. Ainda não há nenhuma regra de negócio.

1. O que a spec pedia

  • Versão do Go declarada em go.mod e no Dockerfile; dependências versionadas.
  • Composição da aplicação com Uber Fx, com injeção por construtores.
  • Configuração validada na inicialização: o processo não sobe com config inválida.
  • Ambiente local com Docker Compose e um .env.example sem segredos.

2. O que foi construído

3. Como funciona

  1. main lê as variáveis de ambiente e monta a Config.
  2. Config inválida: imprime o erro e sai com código 1. Nada mais é criado.
  3. O Fx recebe os construtores e descobre a ordem: logger, pool, handler, router, servidor.
  4. O Fx executa os OnStart: ping no banco e depois abertura da porta HTTP.
  5. O processo fica parado esperando um sinal (SIGTERM ou Ctrl+C).
  6. No sinal, o Fx executa os OnStop na ordem inversa: o servidor HTTP para e depois o pool fecha.

4. Conceitos de Go

Erro é valor de retorno

Go não tem exceção. A função que pode falhar devolve o erro como último retorno e quem chama é obrigado a decidir o que fazer com ele.

cfg, err := config.Load()
if err != nil {
    fmt.Fprintln(os.Stderr, err)
    os.Exit(1)
}

Embrulhar erro com %w

O erro original fica guardado dentro do novo, como a InnerException do C#. É o que permite, mais à frente, classificar erros com errors.Is, uma exigência do desafio.

if err := pool.Ping(ctx); err != nil {
    return fmt.Errorf("ping postgres: %w", err)
}

Visibilidade pela primeira letra

Config, Load e NewPool começam com maiúscula e são públicos. valueOr e writeJSON começam com minúscula e só existem dentro do próprio pacote.

Struct, construtor e método

Não há classes. Os dados ficam em uma struct, o construtor é uma função comum chamada NewAlgo por convenção, e o método é uma função com um receiver, que faz o papel do this.

type HealthHandler struct {
    pool   *pgxpool.Pool
    logger *slog.Logger
}

func NewHealthHandler(pool *pgxpool.Pool, logger *slog.Logger) *HealthHandler {
    return &HealthHandler{pool: pool, logger: logger}
}

func (h *HealthHandler) Live(w http.ResponseWriter, _ *http.Request) {
    writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
}

O * indica ponteiro (referência ao mesmo objeto) e o & cria esse ponteiro. O _ significa "recebo o parâmetro, mas não uso".

context.Context e defer

O context vai sempre como primeiro parâmetro e carrega cancelamento e prazo. No readiness, ele limita o ping a 2 segundos. O defer agenda a linha para o fim da função, com ou sem erro.

ctx, cancel := context.WithTimeout(r.Context(), readinessTimeout)
defer cancel()

if err := h.pool.Ping(ctx); err != nil { ... }

Goroutine

go func() { ... }() inicia uma execução concorrente. O servidor HTTP roda em uma goroutine porque Serve bloqueia até o servidor fechar, e a inicialização precisa continuar.

5. Uber Fx

O Fx é o container de injeção de dependência. Você não registra "interface para implementação": entrega as funções construtoras e ele lê as assinaturas.

func NewRouter(health *HealthHandler) http.Handler

O Fx lê isso como: para criar um http.Handler, preciso de um *HealthHandler. Ele procura quem produz esse tipo e chama na ordem certa.

FunçãoO que faz
fx.Provide(NewX)Registra um construtor. Só executa se alguém precisar do resultado.
fx.Invoke(f)Executa sempre. É o que força a construção do servidor.
fx.Supply(valor)Registra um valor pronto, sem construtor. Usado para a Config.
fx.Module("nome", ...)Agrupa os registros de um pacote.
fx.LifecycleOnde cada componente registra OnStart e OnStop.

A composição inteira, em internal/app/app.go:

func Options(cfg config.Config) fx.Option {
    return fx.Options(
        fx.Supply(cfg),
        fx.StartTimeout(cfg.ShutdownTimeout),
        fx.StopTimeout(cfg.ShutdownTimeout),
        fx.WithLogger(...),
        observability.Module,
        postgres.Module,
        httpapi.Module,
    )
}

E o ciclo de vida do pool, em internal/infra/postgres/pool.go:

lc.Append(fx.Hook{
    OnStart: func(ctx context.Context) error {
        if err := pool.Ping(ctx); err != nil {
            return fmt.Errorf("ping postgres: %w", err)
        }
        return nil
    },
    OnStop: func(context.Context) error {
        pool.Close()
        return nil
    },
})

Por que a ordem de parada sai certa sozinha. O servidor depende do handler, que depende do pool. Então o pool é construído primeiro e registra seu hook primeiro. O Fx executa os OnStop na ordem inversa dos OnStart: o servidor para de receber requisições antes de o pool fechar.

10. Perguntas de revisão

Por que existe um fx.Invoke(func(*http.Server) {}) com corpo vazio?
Porque o Fx só constrói o que alguém pede. Sem essa linha ninguém pediria o servidor, e ele nunca seria criado nem iniciado.
O que acontece se a porta 8080 já estiver em uso?
O net.Listen falha dentro do OnStart, o Fx aborta a inicialização e executa os OnStop do que já tinha iniciado (o pool fecha).
Por que o pool é fechado depois do servidor HTTP no shutdown?
Porque o servidor ainda pode estar terminando requisições que usam o banco. Fechar o pool antes quebraria essas requisições.
Qual a diferença entre fx.Provide e fx.Supply?
Provide registra uma função que cria o valor; Supply registra o valor já pronto.
Por que FromEnv recebe uma função em vez de ler o ambiente diretamente?
Para o teste controlar as variáveis sem alterar o ambiente do processo, o que também permite rodar testes em paralelo.
Com o banco fora do ar, por que /health/live continua 200?
Liveness diz se o processo precisa ser reiniciado. Banco fora não se resolve reiniciando a aplicação; quem sinaliza isso é o readiness.

Spec 02

Money

O tipo que representa dinheiro em todo o sistema: centavos em int64 mais a moeda. Nenhum valor monetário passa por ponto flutuante.

1. O que a spec pedia

  • Value object imutável com valor e moeda.
  • Criação a partir de string decimal, zero por moeda, soma, subtração, negação, comparação e serialização.
  • Proibido float32 e float64 em parsing, cálculo, serialização e persistência. É critério eliminatório.
  • Escala fixa de duas casas e moeda ISO 4217.
  • Rejeitar vazio, NaN, Infinity, notação científica e casas a mais, sem arredondar.
  • Operações só entre valores da mesma moeda.
  • Tratar overflow no parsing, na soma, na subtração e na negação.

2. Por que não usar float

Ponto flutuante guarda números em base 2, e a maioria das frações decimais não tem representação exata nela. Em qualquer linguagem, 0.1 + 0.2 resulta em 0.30000000000000004. Em um sistema financeiro, esse resíduo vira centavo sobrando ou faltando depois de milhares de operações.

A saída é guardar a quantia como inteiro na menor unidade da moeda: 25.00 vira 2500 centavos. Inteiros somam e subtraem de forma exata.

4. Como funciona

Imutabilidade

type Money struct {
    minorUnits int64
    currency   string
}

Os dois campos começam com minúscula, então nenhum outro pacote consegue alterá-los. Os métodos usam receiver por valor (func (m Money), sem *): cada chamada trabalha em uma cópia, e o resultado é sempre um Money novo. É o equivalente a um readonly record struct do C#.

O parser, passo a passo

  1. Separa o sinal -, se houver. O sinal + não é aceito.
  2. Divide no ponto: parte inteira e parte decimal.
  3. Exige só dígitos de 0 a 9 nas duas partes. Isso elimina NaN, Infinity, 1e3, espaços e vírgulas de uma vez.
  4. Rejeita mais de duas casas decimais. Não há arredondamento.
  5. Completa a parte decimal com zeros: "25.5" vira "2550".
  6. Converte dígito a dígito para int64, checando overflow antes de cada multiplicação.

Não se usa strconv.ParseFloat nem nenhuma função de conversão pronta: o parser é uma validação de caracteres seguida de aritmética de inteiros.

Overflow

Em Go, somar além do limite de um int64 não gera erro: o número "dá a volta" e vira negativo, em silêncio. Por isso a checagem acontece antes da operação:

a, b := m.minorUnits, other.minorUnits
if (b > 0 && a > math.MaxInt64-b) || (b < 0 && a < math.MinInt64-b) {
    return Money{}, fmt.Errorf("%w: %s + %s", ErrMoneyOverflow, m, other)
}
return Money{minorUnits: a + b, currency: m.currency}, nil

A leitura é: "se b é positivo e a já está a menos de b do teto, a soma estouraria". A comparação é reescrita de forma que ela própria nunca estoure.

O caso da negação. Um int64 vai de -9.223.372.036.854.775.808 a +9.223.372.036.854.775.807: existe um negativo a mais. Negar o menor valor não tem resultado possível, então Neg() devolve erro nesse caso.

Erros classificáveis

var (
    ErrInvalidMoney     = errors.New("money is not initialized")
    ErrInvalidAmount    = errors.New("invalid money amount")
    ErrInvalidCurrency  = errors.New("invalid currency")
    ErrCurrencyMismatch = errors.New("currency mismatch")
    ErrMoneyOverflow    = errors.New("money amount overflow")
)

São os erros sentinela: variáveis públicas que servem de identidade do erro. Quem recebe o erro pergunta qual é com errors.Is, mesmo que ele tenha sido embrulhado com detalhes pelo %w:

_, err := brl.Add(usd)
if errors.Is(err, domain.ErrCurrencyMismatch) { ... }

Em C# isso seria um catch (CurrencyMismatchException). Mais à frente, a camada HTTP usa essa classificação para decidir entre 400, 409 e 422.

O valor zero de uma struct

Em Go, toda variável nasce com um "valor zero": var m Money é válido para o compilador e contém 0 centavos e moeda vazia. Não existe null para structs. Como o desafio exige rejeitar valores não inicializados, a moeda vazia é o marcador: IsValid() devolve falso, e toda operação e a serialização devolvem ErrInvalidMoney.

JSON

O pacote encoding/json procura dois métodos no tipo. Se existirem, usa-os no lugar do comportamento padrão. É o equivalente a um JsonConverter do C#.

func (m Money) MarshalJSON() ([]byte, error)      // Money  -> JSON
func (m *Money) UnmarshalJSON(data []byte) error  // JSON   -> Money

UnmarshalJSON é o único método com receiver de ponteiro (*Money), porque precisa preencher a variável de quem chamou. Se o conteúdo for inválido, a variável não é alterada.

O campo amount é declarado como string. Se o cliente mandar um número JSON ("amount": 25.00, sem aspas), a decodificação falha.

8. Perguntas de revisão

Por que Add devolve erro, se somar dois inteiros nunca falha em Go?
Por dois motivos: as moedas podem ser diferentes, e a soma pode passar do limite do int64. Go não avisa quando isso acontece; o valor dá a volta e fica negativo.
Por que "25.000" é rejeitado, se vale o mesmo que "25.00"?
A escala é fixa em duas casas e o desafio manda rejeitar escala excedente. Aceitar só quando os dígitos extras são zero seria uma exceção difícil de explicar no contrato.
Como o código garante que ninguém altera um Money depois de criado?
Os campos não são exportados e os métodos têm receiver por valor, então sempre devolvem um Money novo.
O que acontece com var m Money seguido de m.Add(outro)?
Devolve ErrInvalidMoney. O valor zero da struct tem moeda vazia, e isso é tratado como "não inicializado".
Por que amount é string no JSON, e não número?
Um número JSON seria lido como ponto flutuante por quase todo parser, inclusive no cliente. Como string, o valor chega exatamente como foi escrito.
Por que ParseMoney aceita "-5.00", se o desafio proíbe valor negativo nas entradas?
Money também representa diferenças, que podem ser negativas. Quem proíbe negativo em uma aposta ou em um saldo é a entidade que recebe o valor, na spec 03.
Spec 03

Domínio: Wallet, Ledger e WagerTransaction

As regras financeiras do sistema, em Go puro. Nada aqui conhece banco, HTTP ou fila: são structs, métodos e testes que rodam em milissegundos.

1. O que a spec pedia

  • Entidades com estado encapsulado, construtores com validação e métodos explícitos de transição.
  • Criação e reidratação separadas. Reidratar não pode movimentar saldo nem transicionar estado.
  • Erros classificáveis com errors.Is e errors.As; sem panic para regra de negócio.
  • Carteira que nunca fica negativa e cuja versão só sobe quando o saldo muda.
  • Lançamento de ledger imutável, que valida saldoDepois = saldoAntes ± valor.
  • Transação com máquina de estados e as regras de BET, WIN, LOSS, REFUND e ROLLBACK.
  • Um failureCode estável para cada rejeição.

3. Wallet

type Wallet struct {
    id        string
    playerID  string
    balance   Money
    version   int64
    createdAt time.Time

}

Todos os campos são privados. O saldo só muda por Debit e Credit, e os dois devolvem o lançamento de ledger correspondente. Assim é impossível alterar o saldo sem gerar o registro.

func (w *Wallet) Debit(entryID, transactionID string, amount Money, now time.Time) (LedgerEntry, error)

Validar tudo antes de alterar

O método calcula o novo saldo, checa as regras, monta o lançamento e só então grava. Se qualquer passo falhar, a carteira fica intacta:

if newBalance.IsNegative() {
    return LedgerEntry{}, fmt.Errorf("%w: balance %s, debit %s", ErrInsufficientFunds, w.balance, amount)
}

entry, err := NewLedgerEntry(entryID, w.id, transactionID, direction, amount, w.balance, newBalance, now)
if err != nil {
    return LedgerEntry{}, err
}

w.balance = newBalance

4. LedgerEntry

Um lançamento guarda carteira, transação, direção (DEBIT ou CREDIT), valor, saldo antes e saldo depois. O construtor refaz a conta e recusa qualquer combinação que não feche:

switch direction {
case LedgerDebit:
    expected, err = balanceBefore.Sub(amount)
case LedgerCredit:
    expected, err = balanceBefore.Add(amount)
default:
    return LedgerEntry{}, invalid("direction", "must be DEBIT or CREDIT")
}
...
if !expected.Equal(balanceAfter) {
    return LedgerEntry{}, invalid("balanceAfter", "does not match balanceBefore and amount")
}

Não existe método que altere um LedgerEntry. Para corrigir um erro financeiro, cria-se um novo lançamento no sentido contrário. É o que "append-only" significa.

6. ApplyWager: as regras dos cinco tipos

func ApplyWager(tx *WagerTransaction, wallet *Wallet, ref Reference, entryID string, now time.Time) (*LedgerEntry, error)

  1. A carteira é do mesmo jogador? Se não: PLAYER_MISMATCH.
  2. A moeda é a da carteira? Se não: CURRENCY_MISMATCH.
  3. Tem referência? Confere contexto, tipo, estado, valor e se já foi revertida.
  4. Referência ainda não chegou ou está pendente: a transação fica PENDING_REFERENCE.
  5. Define o movimento: débito, crédito ou nenhum.
  6. Movimenta a carteira. Falta de saldo vira rejeição.

Go não tem enum. O idioma é criar um tipo a partir de string e declarar as constantes dele:

10. Perguntas de revisão

Por que Debit devolve um LedgerEntry em vez de só alterar o saldo?
Para que seja impossível mudar o saldo sem produzir o lançamento. O desafio exige que cada mudança financeira tenha o registro correspondente.
Uma aposta sem saldo faz ApplyWager devolver erro?
Não. A função retorna sem erro e a transação fica REJECTED com INSUFFICIENT_FUNDS. É um resultado de negócio que será gravado.
Qual a diferença entre errors.Is e errors.As?
Is compara com um erro específico (uma variável). As procura um erro de um tipo e devolve a struct, dando acesso aos campos.
Por que existem OpenWallet e RehydrateWallet?
Criar define o estado inicial (versão 1). Reidratar restaura o que estava gravado, sem aplicar nenhuma regra de criação.
Como o código impede uma transição a partir de PROCESSED?
PROCESSED não é chave no mapa de transições. A busca devolve lista vazia e transition retorna ErrInvalidTransition.
Um ROLLBACK debita ou credita?
Depende do original: faz o movimento contrário. De uma BET (débito), credita. De um WIN ou REFUND (créditos), debita.
O domínio sozinho impede saldo negativo com duas instâncias rodando?
Não. Cada instância teria a sua cópia da carteira em memória. A garantia entre processos vem do lock e das constraints do banco.
Por que LOSS não altera a versão da carteira?
A versão só sobe quando o saldo muda. LOSS não movimenta nada, então ApplyWager nem chama a carteira.

Spec 04

Schema e migrations

As mesmas regras do domínio, agora escritas no banco. Se a aplicação tiver um bug, ou se duas instâncias disputarem a mesma carteira, o PostgreSQL recusa o que quebraria uma invariante.

1. O que a spec pedia

  • Migrations versionadas, com aplicação e reversão.
  • Saldo nunca negativo, garantido pelo banco.
  • Unicidade da carteira por jogador e moeda, da operação externa e da chave de idempotência.
  • Ledger com um lançamento por transação e carteira, protegido contra edição e exclusão.
  • Schema que distingue operação interna (OPENING) de externa e impede crédito inicial duplicado.
  • Tabelas de inbox e outbox.

5. Os quatro mecanismos usados

CHECK: regra sobre uma linha

CONSTRAINT wallets_balance_non_negative CHECK (balance_minor >= 0)

O banco avalia a expressão em todo INSERT e UPDATE. Se der falso, o comando falha com SQLSTATE 23514. Esta é a rede de segurança contra saldo negativo: mesmo que o lock da aplicação falhasse, o UPDATE não passaria.

O CHECK enxerga só a própria linha. Ele serve para regras como "LOSS tem valor zero" ou "transação rejeitada tem código de falha", mas não para "só existe uma abertura por carteira".

CONSTRAINT wallet_ledger_entries_balance_equation CHECK (
    (direction = 'CREDIT' AND balance_after_minor = balance_before_minor + amount_minor)
    OR (direction = 'DEBIT' AND balance_after_minor = balance_before_minor - amount_minor)
)

É a mesma equação que NewLedgerEntry valida no domínio. A regra existe nos dois lugares de propósito.

UNIQUE e índice único parcial: regra entre linhas

CONSTRAINT wager_transactions_external_key UNIQUE (provider_id, external_transaction_id)

Duas linhas com o mesmo par falham com SQLSTATE 23505. É isso que impede a mesma operação de ser aplicada duas vezes quando duas instâncias a recebem ao mesmo tempo: uma insere, a outra recebe o erro.

Um índice único parcial aplica a unicidade só às linhas que passam em um filtro:

CREATE UNIQUE INDEX wager_transactions_one_opening_per_wallet
    ON wager_transactions (wallet_id)
    WHERE kind = 'OPENING';

CREATE UNIQUE INDEX wager_transactions_one_processed_reversal
    ON wager_transactions (reference_transaction_id)
    WHERE status = 'PROCESSED' AND kind IN ('REFUND', 'ROLLBACK');

O primeiro permite muitas transações por carteira, mas só uma OPENING. O segundo permite várias reversões rejeitadas da mesma aposta, mas só uma processada. É a regra "uma reversão por transação" da spec 03, agora à prova de concorrência.

NULL em UNIQUE. O Postgres trata cada NULL como diferente dos outros. Por isso as transações OPENING, que têm provider_id nulo, não colidem entre si na constraint (provider_id, external_transaction_id).

Chave estrangeira composta: coerência entre tabelas

FOREIGN KEY (wallet_id, currency)       REFERENCES wallets (id, currency),
FOREIGN KEY (transaction_id, wallet_id) REFERENCES wager_transactions (id, wallet_id)

Uma FK comum garante que a carteira existe. A composta garante mais: que o lançamento está na moeda da carteira e pertence à mesma carteira da transação. Para isso a tabela de destino precisa de um UNIQUE nas mesmas colunas, e é por isso que wallets tem UNIQUE (id, currency), que parece redundante.

Trigger: o ledger append-only

CREATE FUNCTION reject_wallet_ledger_entry_change() RETURNS trigger
    LANGUAGE plpgsql AS
$$
BEGIN
    RAISE EXCEPTION 'wallet_ledger_entries is append-only: % is not allowed', TG_OP
        USING ERRCODE = 'restrict_violation';
END;
$$;

CREATE TRIGGER wallet_ledger_entries_append_only
    BEFORE UPDATE OR DELETE ON wallet_ledger_entries
    FOR EACH ROW EXECUTE FUNCTION reject_wallet_ledger_entry_change();

Um trigger é uma função que o banco executa quando algo acontece na tabela. Esta roda antes de cada UPDATE ou DELETE e sempre lança erro; TG_OP é o nome da operação tentada. Só INSERT passa.

Há um segundo trigger para TRUNCATE, porque o trigger por linha não dispara nesse comando.

6. Interno e externo na mesma tabela

OPENING não tem provedor, ID externo, chave, hash, rodada nem jogo. As outras operações têm todos. As colunas são anuláveis e um CHECK exige um dos dois formatos, sem meio-termo:

CONSTRAINT wager_transactions_origin CHECK (
    (kind = 'OPENING' AND status = 'PROCESSED'
        AND num_nonnulls(provider_id, external_transaction_id, ...) = 0)
    OR
    (kind <> 'OPENING'
        AND num_nulls(provider_id, external_transaction_id, ...) = 0)
)

num_nulls e num_nonnulls contam quantos argumentos são nulos ou não nulos. Evitam uma fila de IS NULL AND ... IS NULL.

11. Perguntas de revisão

Se o domínio já impede saldo negativo, para que serve o CHECK?
O domínio valida a cópia em memória de uma instância. O CHECK vale para todas as instâncias e para qualquer bug da aplicação.

Os dois campos são NULL nelas, e o Postgres não considera dois NULL iguais.
Como o ledger fica imutável?

O que o CHECK não consegue fazer?

Para que serve UNIQUE (id, currency) em wallets, se id já é único?
Para ser o destino da FK composta do ledger, que garante lançamento na moeda da carteira.
Como o app sabe que o schema está pronto?
No Compose ele depende do migrate com service_completed_successfully.
Por que o teste de schema é pulado no go test ./... comum?

Spec 05

Persistência e transação SQL

A ponte entre o domínio e o banco: repositórios com SQL escrito à mão, uma transação compartilhada por todos eles e o lock por carteira que impede duas instâncias de gastarem o mesmo saldo.

1. O que a spec pedia

  • pgx com SQL explícito; transações, locks e constraints visíveis no código.
  • Um único mecanismo que delimita a transação SQL, compartilhada por todos os repositórios de um caso de uso.
  • Lock por carteira. Lock global é proibido; carteiras diferentes avançam em paralelo.
  • Nenhuma atualização confirmada pode ser perdida.
  • Todo I/O recebe context.Context e respeita cancelamento.
  • Falha transitória distinguível de falha permanente.

4. A transação viaja no context

func (m *TxManager) WithinTx(ctx context.Context, fn func(ctx context.Context) error) error {
    if _, ok := ctx.Value(txContextKey{}).(pgx.Tx); ok {
        return fn(ctx)                      // já existe transação: entra nela
    }

    tx, err := m.pool.Begin(ctx)
    if err != nil {
        return translate(err)
    }
    defer func() { _ = tx.Rollback(context.WithoutCancel(ctx)) }()

    if err := fn(context.WithValue(ctx, txContextKey{}, tx)); err != nil {
        return err                          // o defer faz o rollback
    }
    return translate(tx.Commit(ctx))
}
  1. Begin pega uma conexão do pool e abre a transação.
  2. context.WithValue cria um novo ctx que carrega a transação.
  3. A função do caso de uso recebe esse ctx e o repassa a cada repositório.
  4. Cada repositório procura a transação no ctx. Achou: usa ela. Não achou: usa o pool.
  5. Retornou nil: commit. Retornou erro: rollback.
func querierFrom(ctx context.Context, pool *pgxpool.Pool) querier {
    if tx, ok := ctx.Value(txContextKey{}).(pgx.Tx); ok {
        return tx
    }
    return pool
}

O caso de uso não vê pgx.Tx em lugar nenhum. Ele só escreve:

5. O lock por carteira

SELECT id::text, player_id, currency, balance_minor, version, created_at, updated_at
  FROM wallets
 WHERE id = $1
   FOR UPDATE

FOR UPDATE trava a linha até o fim da transação. Outra transação que pedir a mesma linha com FOR UPDATE fica parada esperando. Quando a primeira termina, a segunda lê o saldo já atualizado.

InstanteInstância A (aposta de 80)Instância B (aposta de 80)
1GetForUpdate: lê saldo 100
2GetForUpdate: espera
3Debita, grava saldo 20, commit
4Lê saldo 20
5Domínio rejeita: INSUFFICIENT_FUNDS

Sem o lock, as duas leriam 100 e as duas gravariam 20: uma aposta sumiria do saldo. Esse é o lost update.

O lock é da linha, não da tabela. Uma aposta em outra carteira não espera ninguém.

Duas proteções extras

UPDATE wallets
   SET balance_minor = $2, version = $3, updated_at = $4
 WHERE id = $1 AND version = $3 - 1
  • Guarda de versão. O UPDATE só acerta a linha se a versão no banco for a anterior à nova. Se alguém gravou sem o lock, nenhuma linha é afetada e o repositório devolve ErrConcurrentUpdate.
  • GetForUpdate fora de transação retorna erro. Sem transação o lock seria solto no mesmo instante.

Com o CHECK (balance_minor >= 0) da spec 04, são três camadas contra saldo errado: lock, guarda de versão e constraint.

É aqui que os nomes explícitos das constraints da spec 04 são usados: o mesmo código 23505 vira erros diferentes conforme a constraint violada.

return fmt.Errorf("%w: %w", application.ErrDuplicateIdempotencyKey, pgErr)

Dois %w encadeiam os dois erros. errors.Is(err, application.ErrDuplicateIdempotencyKey) é verdadeiro, e o erro original do Postgres continua acessível para o log.

Transitório × permanente. Transitório: repetir a mesma chamada mais tarde pode funcionar (banco reiniciando, deadlock). Vai virar 503 no HTTP e reentrega no SQS. Permanente: repetir dá o mesmo resultado. Essa distinção é exigida pelo desafio e decide o que vai para a DLQ.

Depois de uma violação de constraint, o PostgreSQL marca a transação como abortada: qualquer comando seguinte falha. Por isso o caso de uso retorna o erro em vez de tentar continuar.

11. Perguntas de revisão

Como um repositório sabe que está dentro de uma transação?
Ele procura a transação no context. O TxManager a colocou lá com context.WithValue.
Por que a interface WalletRepository fica em application e não em postgres?
Porque quem usa define o contrato. Assim application não importa nada de banco.
O que FOR UPDATE trava, e até quando?
As linhas retornadas pelo SELECT, até o commit ou rollback da transação.
O que é lost update e como é evitado aqui?
Duas transações leem o mesmo saldo e uma sobrescreve a outra. O lock faz a segunda ler só depois do commit da primeira.
Para que serve a guarda de versão se já existe o lock?
Para transformar um uso errado (gravar sem lock) em erro, em vez de corromper o saldo em silêncio.
Por que o rollback usa context.WithoutCancel?
Se o ctx original foi cancelado, o rollback feito com ele também seria cancelado.
Qual a diferença entre ErrUnavailable e ErrInvariantViolation?
O primeiro é transitório: vale tentar de novo. O segundo é permanente: o banco recusou algo que o domínio não deveria ter produzido.
O que fx.As faz?
Registra o resultado de um construtor como uma interface, para que os consumidores peçam a interface e não o tipo concreto.

Carteira: abertura, leitura e ledger paginado

O primeiro fluxo de ponta a ponta. Uma requisição HTTP atravessa todas as camadas construídas até aqui: handler, caso de uso, domínio, repositórios e banco.

3. O caminho de uma requisição

  1. Middleware lê ou gera o X-Correlation-Id e o coloca no context.
  2. Handler decodifica o JSON e chama o caso de uso. Não tem regra de negócio.
  3. Caso de uso cria os objetos de domínio e abre a transação SQL.
  4. Domínio valida: OpenWallet, NewOpeningTransaction, NewLedgerEntry, eventos.
  5. Repositórios gravam tudo dentro da mesma transação.
  6. Handler converte o resultado, ou o erro, em resposta HTTP.

Cada camada conhece só a de dentro. O handler não sabe que existe Postgres; o caso de uso não sabe que existe HTTP. É por isso que o mesmo caso de uso vai servir ao consumidor SQS na spec 11.

4. O caso de uso de abertura

func (uc *OpenWallet) Execute(ctx context.Context, in OpenWalletInput) (*domain.Wallet, error) {
    now := uc.clock.Now()
    wallet, err := domain.OpenWallet(uc.ids.NewID(), in.PlayerID, in.InitialBalance, now)
    if err != nil {
        return nil, err
    }

    err = uc.tx.WithinTx(ctx, func(ctx context.Context) error {
        if err := uc.wallets.Insert(ctx, wallet); err != nil {
            return err
        }
        if wallet.Balance().IsZero() {
            return nil
        }
        return uc.recordOpeningCredit(ctx, wallet, in.CorrelationID)
    })
    ...
}
  • A validação do domínio acontece antes de abrir a transação: entrada inválida não gasta conexão.
  • Saldo zero sai cedo: só a carteira é gravada.
  • Saldo positivo grava a OPENING, o lançamento e os dois eventos. Qualquer erro desfaz tudo, inclusive a carteira.
  • Jogador e moeda repetidos: o INSERT viola o UNIQUE, o repositório devolve ErrWalletAlreadyExists e o handler responde 409. Não há consulta prévia "já existe?": duas requisições simultâneas passariam por ela.

Por que a versão é 1 e não 2. A carteira já nasce com o saldo. Se o caso de uso criasse com zero e chamasse wallet.Credit, a versão subiria para 2, e o desafio fixa 1 na abertura. Por isso o lançamento de abertura é montado direto com NewLedgerEntry (de 0.00 para o saldo inicial).

Relógio e IDs como dependência

type Clock interface       { Now() time.Time }
type IDGenerator interface { NewID() string }

O domínio recebe id e now por parâmetro (spec 03). Quem os fornece é o caso de uso, por duas interfaces pequenas. Em produção são o relógio do sistema e UUID v7; em teste podem ser valores fixos.

O relógio trunca em microssegundo, que é a precisão do PostgreSQL. Sem isso, o horário em memória teria nanossegundos e o relido do banco não seria igual.

12. Perguntas de revisão

Por que não consultar "já existe carteira?" antes de inserir?
Duas requisições simultâneas passariam pela consulta. O UNIQUE do banco é a única checagem que vale entre instâncias.
O que garante que carteira, transação, lançamento e eventos são gravados juntos?
Tudo acontece dentro de um WithinTx. Qualquer erro retornado faz rollback de todos.
Por que o evento vai para uma tabela em vez de ir direto para o SQS?
Para ser confirmado no mesmo commit do saldo. Publicar direto permitiria evento sem commit, ou commit sem evento.
O que é embedding e o que ele causa no JSON?
Colocar um tipo dentro de uma struct sem nome de campo. Os campos sobem de nível: o envelope fica ao lado de data.

Inserções durante a leitura não fazem repetir nem pular itens, e páginas distantes custam o mesmo que a primeira.
Por que a consulta do ledger pede limit + 1?

Por que Clock é uma interface?
Para o caso de uso não ler o relógio direto. Em teste dá para fixar o horário; em produção ele é truncado na precisão do banco.

Spec 07

Operações e idempotência

O coração do desafio: um único caso de uso que aplica cada operação exatamente uma vez, mesmo que ela chegue 50 vezes ao mesmo tempo, em instâncias diferentes, ou de novo depois de um reinício.

3. O que é idempotência

Uma operação é idempotente quando executá-la duas vezes tem o mesmo efeito de executá-la uma. Redes falham: o provedor manda uma aposta, não recebe a resposta e manda de novo. O saldo só pode ser debitado uma vez, e as duas respostas precisam ser iguais.

Para isso cada requisição traz uma chave de idempotência, e o servidor guarda, junto com a transação, um hash do conteúdo.

ChegouResposta
Chave nova, operação novaProcessa
Mesma chave, mesmo hashResultado gravado, idempotentReplay: true
Mesma chave, hash diferente409 IDEMPOTENCY_KEY_CONFLICT
Chave nova, mas externalTransactionId já usado409 EXTERNAL_TRANSACTION_CONFLICT

O hash existe por causa da terceira linha: sem ele, um cliente com bug reutilizando a chave receberia como resposta o resultado de outra operação, sem perceber.

4. O hash do payload

func payloadHash(in ProcessWagerInput) (string, error) {
    fields := map[string]any{
        "providerId":            in.ProviderID,
        "externalTransactionId": in.ExternalTransactionID,
        "playerId":              in.PlayerID,
        "walletId":              in.WalletID,
        "roundId":               in.RoundID,
        "gameId":                in.GameID,
        "kind":                  in.Kind,
        "money": map[string]string{"amount": in.Money.Amount(), "currency": in.Money.Currency()},
    }
    if in.ReferenceExternalTransactionID != "" {
        fields["referenceExternalTransactionId"] = in.ReferenceExternalTransactionID
    }

    canonical, err := json.Marshal(fields)
    ...
    sum := sha256.Sum256(canonical)
    return hex.EncodeToString(sum[:]), nil
}
  • JSON canônico: a mesma informação precisa virar sempre os mesmos bytes. {"a":1,"b":2} e {"b":2,"a":1} são o mesmo objeto, mas dariam hashes diferentes. O encoding/json escreve as chaves de um map em ordem alfabética, e é isso que torna a saída canônica.
  • Normalização: in.Money.Amount() devolve sempre duas casas. "25", "25.0" e "25.00" geram o mesmo hash.
  • Fora do hash: a chave de idempotência e o correlation ID. São do transporte, não da operação. Por isso HTTP e SQS geram o mesmo hash para o mesmo conteúdo.
  • sha256.Sum256 devolve um array de 32 bytes; sum[:] o transforma em slice para o hex.

Um teste fixa o hash da aposta do enunciado em um valor calculado por fora (sha256sum). Se alguém mudar o algoritmo, o teste falha: mudar o hash invalidaria todos os registros já gravados.

5. O caso de uso, passo a passo

  1. Valida a entrada e calcula o hash.
  2. Abre a transação SQL.
  3. GetForUpdate na carteira: trava a linha.
  4. Procura duplicata: pela chave, depois pelo ID externo.
  5. Resolve a referência, se houver.
  6. domain.ApplyWager decide: processa, rejeita ou espera.
  7. Grava a transação. Se o saldo mudou, grava saldo e lançamento.
  8. Grava os eventos na outbox.
  9. Commit.

Tudo entre os passos 2 e 9 é uma transação só. Uma rejeição de negócio também percorre o caminho inteiro: é gravada como REJECTED, gera evento e pode ser devolvida igual em um replay.

Por que o lock vem antes da checagem de duplicata

InstanteRequisição ARequisição B (idêntica)
1Trava a carteira
2Duplicata? NãoTenta travar: espera
3Debita, grava, commit
4Trava a carteira
5Duplicata? Sim: devolve o resultado de A

Com a ordem invertida, as duas perguntariam "já existe?" antes de qualquer uma gravar, as duas ouviriam "não", e as duas tentariam debitar.

Quando o lock não basta

O lock é por carteira. Se a mesma chave chegar com walletId diferentes, cada requisição trava uma carteira e nenhuma espera a outra. Quem decide é o UNIQUE (provider_id, idempotency_key) da spec 04:

for attempt := 1; ; attempt++ {
    err = uc.tx.WithinTx(ctx, func(ctx context.Context) error { ... })
    if !lostDuplicateRace(err) || attempt == maxProcessAttempts {
        break
    }
}
  1. O INSERT perdedor viola o UNIQUE.
  2. O repositório devolve ErrDuplicateIdempotencyKey e a transação inteira sofre rollback.
  3. O caso de uso tenta de novo, em uma transação nova.
  4. Agora a checagem de duplicata encontra a linha: replay ou conflito.

É a regra da spec 05 em uso: depois de uma violação de constraint, a transação está abortada, então não se continua nela.

Duas camadas. O lock resolve o caso comum sem erro nenhum. A constraint resolve o caso que o lock não cobre. Nenhuma das duas depende de memória do processo, então funciona igual com três instâncias.

Simulando outra instância

A corrida entre carteiras diferentes depende de milissegundos: não dá para reproduzir só disparando goroutines. O teste a força com um repositório falso que, no primeiro Insert, grava antes uma transação "gêmea" por outra conexão:

func (r *racingWagers) Insert(ctx context.Context, tx *domain.WagerTransaction) error {
    if !r.raced {
        r.raced = true
        // context.Background() não carrega transação: a gêmea é confirmada em outra conexão
        postgres.NewWagerTransactionRepository(r.pool).Insert(context.Background(), r.twin(tx))
    }
    return r.WagerTransactionRepository.Insert(ctx, tx)
}

O Insert verdadeiro então viola o UNIQUE. O teste confere que a tentativa perdedora foi desfeita por inteiro (saldo intacto, nenhum lançamento, nenhum evento) e que o resultado final é replay ou conflito.

Ao escrever esse teste apareceu um detalhe do PostgreSQL: a gêmea na mesma carteira ficaria travada para sempre. Inserir uma linha com chave estrangeira pede um lock leve na linha referenciada, e o FOR UPDATE bloqueia até esse. Ou seja, com o lock da carteira preso, nenhuma outra transação consegue nem inserir uma operação para ela.

10. Perguntas de revisão

Para que serve o hash, se já existe a chave de idempotência?
Para detectar a mesma chave com conteúdo diferente. Sem ele, o servidor devolveria o resultado de outra operação.
O que torna o JSON canônico?
Chaves em ordem fixa (alfabética) e valor monetário normalizado. A mesma operação gera sempre os mesmos bytes.
Por que a chave de idempotência não entra no hash?
Ela é do transporte. O hash descreve a operação, e precisa ser igual por HTTP e por SQS.
Por que travar a carteira antes de procurar duplicata?
Para que a segunda requisição idêntica só procure depois que a primeira gravou.
O que acontece quando a mesma chave chega para carteiras diferentes ao mesmo tempo?
O lock não serializa. O UNIQUE recusa o segundo INSERT, a transação é desfeita e a nova tentativa encontra a linha.
De onde vem o saldo devolvido em um replay?
Da coluna result_balance_minor da transação, gravada no processamento original.
Aposta sem saldo responde 400 ou 422? Por quê?
422. É um resultado de negócio definitivo, gravado como REJECTED. 400 é entrada malformada, que não é gravada.
A idempotência sobrevive a um reinício?
Sim. Chave, hash e resultado estão no PostgreSQL; nada fica em memória.

Spec 08

Reversões e referências pendentes

Um REFUND pode chegar antes da aposta que ele devolve. Em vez de recusar, o serviço guarda a operação como pendente e um worker em segundo plano tenta de novo, com intervalos cada vez maiores, até a aposta chegar ou o prazo acabar.

1. O que a spec pedia

  • Referência não encontrada: gravar PENDING_REFERENCE e responder 202 (já feito na spec 07).
  • Um worker que tenta de novo com backoff exponencial.
  • O estado da espera fica no banco e sobrevive a reinício.
  • Várias instâncias do worker não processam a mesma pendência duas vezes.
  • Esgotado o limite: REJECTED com REFERENCE_NOT_FOUND.
  • Dois REFUND da mesma aposta em paralelo: um processado, um rejeitado.

3. Onde fica o estado da espera

Se a contagem de tentativas ficasse em memória, um reinício zeraria tudo. Por isso ela fica em três colunas novas de wager_transactions:

ColunaUso
reference_attemptsQuantas consultas não acharam a referência
next_reference_attempt_atQuando consultar de novo
correlation_idO correlation ID da requisição original
 
CONSTRAINT wager_transactions_next_attempt_only_while_waiting CHECK (
    (status = 'PENDING_REFERENCE') = (next_reference_attempt_at IS NOT NULL)
)

O CHECK compara dois booleanos: a data existe se e somente se a transação está esperando. Uma pendência sem data nunca seria pega de novo pelo worker; o banco recusa esse estado.

O correlation_id existe porque o worker conclui a operação minutos depois, fora de qualquer requisição. Sem a coluna, os eventos emitidos por ele não poderiam ser ligados ao pedido original.

4. Backoff exponencial

Consultar o banco a cada segundo por uma referência que pode demorar minutos é desperdício. No backoff exponencial a espera dobra a cada falha, até um teto.

func (p ReferenceRetryPolicy) delayAfter(attempts int) time.Duration {
    delay := p.BaseDelay
    for i := 1; i < attempts; i++ {
        if delay >= p.MaxDelay/2 {
            return p.MaxDelay
        }
        delay *= 2
    }
    return min(delay, p.MaxDelay)
}

5. Uma fila dentro do PostgreSQL

As pendências formam uma fila: "tudo que está PENDING_REFERENCE e com a data vencida". Com três instâncias do serviço, três workers leem essa fila ao mesmo tempo. O problema é entregar cada item a um só.

UPDATE wager_transactions
   SET next_reference_attempt_at = $2          -- agora + 30s
 WHERE id IN (
    SELECT id FROM wager_transactions
     WHERE status = 'PENDING_REFERENCE' AND next_reference_attempt_at <= $1
     ORDER BY next_reference_attempt_at
     LIMIT $3
       FOR UPDATE SKIP LOCKED
 )
RETURNING id::text, wallet_id::text
  • FOR UPDATE trava as linhas escolhidas.
  • SKIP LOCKED faz o comando pular as linhas que outra transação já travou, em vez de esperar por elas. Dois workers rodando ao mesmo tempo recebem conjuntos diferentes.
  • RETURNING devolve as linhas alteradas, como um SELECT embutido no UPDATE.

O lock some quando esse comando termina. O que protege a pendência depois disso é a data empurrada 30 segundos para a frente: para os outros workers ela deixou de estar vencida. Isso é uma reserva com prazo (em inglês, lease).

Por que o prazo. Se a instância morrer logo depois de reservar, ninguém precisa "liberar" nada: em 30 segundos a data vence e outra instância pega a pendência. Um teste simula isso reservando sem resolver.

6. Resolver uma pendência

  1. Abrir transação SQL e travar a carteira (GetForUpdate).
  2. Reler a transação. Se não está mais PENDING_REFERENCE, outra instância já resolveu: sair.
  3. Procurar a referência e chamar domain.ApplyWager.
  4. Ainda esperando e há tentativas: somar uma tentativa, gravar a próxima data, sair.
  5. Ainda esperando e sem tentativas: marcar REJECTED com REFERENCE_NOT_FOUND.
  6. Gravar transação, saldo, lançamento e eventos.

Os passos de 3 em diante usam o mesmo código do endpoint HTTP. A parte comum foi extraída para wagerOutcome.record, chamada pelos dois casos de uso.

Ordem dos locks. O worker trava a carteira e só depois mexe na linha da transação, na mesma ordem do endpoint HTTP. Se ele segurasse a linha da transação e depois pedisse a carteira, poderia cruzar com uma requisição que tem a carteira e quer alterar aquela linha: cada um esperando o outro, um deadlock. Por isso a reserva (passo anterior) solta o lock da linha antes de a resolução começar.

7. Despertar: não esperar o backoff à toa

O backoff serve para a referência que não chegou. Quando ela chega, esperar o resto do intervalo seria atraso sem motivo. Ao gravar uma transação em estado final, a mesma transação SQL antecipa as pendências que apontam para ela:

UPDATE wager_transactions
   SET next_reference_attempt_at = $3          -- agora
 WHERE provider_id = $1 AND reference_external_transaction_id = $2
   AND status = 'PENDING_REFERENCE' AND next_reference_attempt_at > $3

O worker pega a pendência no ciclo seguinte (até 1 segundo). Isso também resolve cadeias: um ROLLBACK esperando um REFUND que espera uma BET é concluído em dois ciclos.

8. O worker: goroutine, ticker e cancelamento

func (w *ReferenceResolver) Run(ctx context.Context) {
    ticker := time.NewTicker(w.interval)
    defer ticker.Stop()

    for {
        w.drain(ctx)
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
        }
    }
}
  • time.NewTicker cria um canal (ticker.C) que recebe um valor a cada intervalo. É o equivalente a um setInterval ou a um PeriodicTimer do C#.
  • select espera o que acontecer primeiro: o contexto ser cancelado ou o próximo tique.
  • drain repete enquanto o lote volta cheio, e para depois de um erro, para não girar em falso com o banco fora do ar.
ctx, cancel := context.WithCancel(context.Background())
done := make(chan struct{})

lc.Append(fx.Hook{

            defer close(done)

  • O contexto que o Fx passa ao OnStart expira quando a inicialização termina. A goroutine precisa de um contexto próprio.
  • done é um canal fechado quando Run retorna. No OnStop, cancel() pede a parada e <-done espera a pendência em andamento terminar.
  • Se demorar mais que o prazo de desligamento, stopCtx.Done() vence e o Fx segue. A transação SQL interrompida é desfeita e a reserva vence sozinha.

10. Para fixar

O que SKIP LOCKED faz de diferente de um FOR UPDATE comum?
Pula as linhas já travadas em vez de esperar. Cada worker recebe linhas diferentes e nenhum fica parado.
O lock do SKIP LOCKED dura um comando. O que impede outro worker de pegar a pendência logo depois?
A data da próxima tentativa foi empurrada 30 segundos. Para os outros, ela não está vencida.
O que acontece se a instância morrer com uma pendência reservada?
Nada precisa ser liberado. A reserva vence e outra instância assume.
Por que o worker trava a carteira antes de mexer na transação?
Para usar a mesma ordem de locks do endpoint HTTP e não haver deadlock; e para que reversões da mesma carteira sejam decididas uma de cada vez.
Se a aposta chega, o REFUND espera o backoff terminar?
Não. A gravação da aposta antecipa a data das pendências que a referenciam.
Por que guardar o correlation_id na transação?
O worker roda fora de qualquer requisição; sem a coluna, os eventos dele não se ligariam ao pedido original.

Spec 09

Autenticação e autorização

Até aqui qualquer um podia chamar qualquer endpoint dizendo ser qualquer provedor. Agora todo endpoint de negócio exige um token emitido pelo Keycloak, e é o token, não o corpo da requisição, que diz quem está chamando.

1. O que a spec pedia

  • Provedor de identidade externo (OAuth 2.0 / OIDC), fluxo client_credentials. Sem senha e sem token próprio.
  • O providerId do corpo precisa bater com o do token.
  • Provedor só vê as próprias transações; carteira só para o serviço interno; health checks públicos.
  • Sem token ou token inválido: 401. Token válido sem permissão: 403. Transação de outro provedor: 404.
Eliminatório. Endpoint de negócio sem autenticação efetiva, ou acesso a transação de outro provedor, desclassifica a entrega.

2. Autenticação × autorização

PerguntaFalha
AutenticaçãoQuem é você? O token é legítimo?401 Unauthorized
AutorizaçãoVocê pode fazer isto?403 Forbidden

O nome do 401 engana: ele significa "não autenticado". O 403 é o "não autorizado" de verdade.

3. O fluxo client_credentials

É o fluxo OAuth para serviço falando com serviço, sem usuário humano. Cada provedor é um client no Keycloak, com um identificador e um segredo.

  1. O provedor manda client_id e client_secret ao Keycloak.
  2. O Keycloak devolve um access token (um JWT) válido por 5 minutos.
  3. O provedor chama o nosso serviço com Authorization: Bearer <token>.
  4. O serviço confere o token sozinho, sem chamar o Keycloak a cada requisição.
curl -s -X POST http://localhost:8081/realms/wagering/protocol/openid-connect/token \
  -d grant_type=client_credentials -d client_id=provider-a -d client_secret=provider-a-secret

4. JWT e JWKS

Um JWT tem três partes em base64url separadas por ponto: cabeçalho.conteúdo.assinatura. O conteúdo de um token do provider-a:

{
  "iss": "http://localhost:8081/realms/wagering",
  "aud": "wagering-service",
  "azp": "provider-a",
  "exp": 1791979240,
  "realm_access": { "roles": ["provider"] },
  "provider_id": "provider-a"
}
  • iss (issuer): quem emitiu. aud (audience): para quem o token foi feito. exp: quando expira.
  • azp: o client que pediu o token. realm_access.roles: os papéis. provider_id: claim que criamos no Keycloak.
  • Qualquer um lê o conteúdo; ele não é secreto. O que impede a falsificação é a assinatura.

O Keycloak assina com uma chave privada RSA que só ele tem. A chave pública correspondente fica publicada em um endereço chamado JWKS (JSON Web Key Set). O nosso serviço baixa essas chaves e confere a assinatura localmente. O cabeçalho do token traz um kid (key id) que diz qual chave usar.

Por que conferir aud. O mesmo Keycloak pode emitir tokens para vários sistemas. Sem checar a audiência, um token feito para outro serviço do mesmo realm seria aceito aqui.

7. Middleware em Go e a identidade no context

Em Go um middleware é uma função que recebe um http.Handler e devolve outro, que faz algo antes (ou em vez) de chamar o próximo. É o mesmo papel do middleware do ASP.NET ou do Express.

func authenticate(verifier TokenVerifier, logger *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            raw, ok := bearerToken(r)
            if !ok { /* 401 */ return }
            principal, err := verifier.Verify(r.Context(), raw)
            if err != nil { /* 401 */ return }
            next.ServeHTTP(w, r.WithContext(auth.WithPrincipal(r.Context(), principal)))
        })
    }
}
  • r.WithContext cria uma cópia da requisição com um contexto novo, que carrega o Principal. Os handlers o leem com auth.PrincipalFrom(ctx).

  • O middleware depende da interface TokenVerifier, não do verificador concreto. Os testes HTTP usam um verificador falso; o verdadeiro é testado no pacote auth.

Spec 10

Outbox e publicação de eventos

Desde a spec 06 cada mudança de saldo grava eventos na tabela outbox_events, na mesma transação. Agora um worker tira esses eventos do banco e os publica numa fila SQS, sem perder nenhum e sem trocar a ordem dos eventos de uma carteira.

1. O que a spec pedia

  • Nenhum evento sai antes do commit; nenhum evento confirmado se perde.
  • Vários publishers em paralelo sem publicar o mesmo evento ao mesmo tempo.
  • Retry com backoff; trabalho de instância morta retomado por outra.
  • Republicação mantém o mesmo eventId.
  • Fila wager-events.fifo, com MessageGroupId = carteira e MessageDeduplicationId = eventId.
Eliminatório. Publicar um evento antes do commit.

2. Por que a outbox existe

A tentação é publicar na fila logo depois de gravar no banco. Os dois são sistemas separados, e não há transação que cubra os dois:

OrdemFalha no meioResultado
Publica, depois commitaO commit falhaEvento de um saldo que nunca mudou
Commita, depois publicaO processo morre antes de publicarSaldo mudou e ninguém fica sabendo

A transactional outbox resolve gravando o evento numa tabela do mesmo banco, na mesma transação do saldo. Ou os dois existem, ou nenhum. Publicar vira uma segunda etapa que pode ser repetida até dar certo.

  1. O caso de uso grava saldo, lançamento e evento numa transação só.
  2. O worker lê os eventos não publicados, envia ao SQS e marca como publicados.

3. At-least-once

Se o processo morrer depois de enviar e antes de marcar, o evento será enviado de novo. Não existe forma de evitar isso por completo: entre "enviei" e "anotei que enviei" sempre há um instante de risco. Por isso a garantia é pelo menos uma vez (at-least-once), e o consumidor precisa ser idempotente, deduplicando pelo eventId.

O SQS FIFO ajuda: mensagens com o mesmo MessageDeduplicationId em menos de 5 minutos são descartadas. Depois disso, a duplicata passa.

4. O problema da ordem

Numa fila FIFO, mensagens do mesmo MessageGroupId são entregues na ordem em que foram enviadas. Com o grupo sendo a carteira, quem consome vê os saldos de uma carteira na sequência certa. Mas só se nós enviarmos na sequência certa.

Com dois publishers reservando eventos soltos, o publisher A poderia pegar o evento 1 da carteira e o B o evento 2; se B for mais rápido, o 2 sai antes. Por isso a reserva é feita por carteira inteira.

5. A reserva por carteira

WITH heads AS (
    SELECT o.aggregate_id FROM outbox_events o
     WHERE o.published_at IS NULL
       AND o.next_attempt_at <= $1
       AND (o.locked_until IS NULL OR o.locked_until <= $1)
       AND NOT EXISTS (                     -- é o mais antigo não publicado da carteira
            SELECT 1 FROM outbox_events p
             WHERE p.aggregate_id = o.aggregate_id
               AND p.published_at IS NULL AND p.sequence < o.sequence)
     ORDER BY o.sequence
     LIMIT $3
       FOR UPDATE SKIP LOCKED
), claimed AS (
    SELECT id FROM (
        SELECT e.id, row_number() OVER (PARTITION BY e.aggregate_id ORDER BY e.sequence) AS position
          FROM outbox_events e JOIN heads h ON h.aggregate_id = e.aggregate_id
         WHERE e.published_at IS NULL) ranked
     WHERE position <= $4
)
UPDATE outbox_events SET locked_until = $2      -- agora + 30s
 WHERE id IN (SELECT id FROM claimed)
RETURNING ...
  • heads escolhe a cabeça de cada carteira: o evento não publicado mais antigo. Só ela é travada.
  • Outro publisher rodando ao mesmo tempo pula a cabeça travada (SKIP LOCKED) e também não pega o evento 2, porque para ele a cabeça ainda está não publicada e o NOT EXISTS exclui o 2.
  • claimed pega os eventos não publicados dessas carteiras, até $4 por carteira. row_number() OVER (PARTITION BY ...) é uma função de janela: numera as linhas dentro de cada carteira, sem agrupar.
  • O UPDATE grava a reserva de 30 segundos, a mesma ideia de lease da spec 08. Depois do comando, é ela que mantém os outros afastados.
  • CTE (WITH ... AS) é uma consulta com nome, usada pelas partes seguintes do mesmo comando.

Uma cabeça com next_attempt_at no futuro (esperando backoff) segura a carteira inteira. É intencional: o evento seguinte não pode passar na frente.

Spec 11

Consumidor SQS, inbox e DLQ

A segunda porta de entrada: provedores também podem mandar operações pela fila wager-transactions.fifo. O resultado financeiro tem que ser o mesmo do HTTP, mesmo com a mensagem chegando duas vezes, o processo morrendo no meio ou o banco fora do ar.

1. O que a spec pedia

  • Usar o mesmo caso de uso do HTTP, com data.idempotencyKey como chave.
  • Inbox: gravar (consumerName, messageId) e o hash do corpo na mesma transação do saldo, ledger e outbox.
  • Remover a mensagem da fila só depois do commit.
  • Falha transitória: tentar de novo com backoff. Erro permanente ou tentativas esgotadas: DLQ.
  • No SIGTERM, parar de buscar e terminar ou devolver o que está em andamento.
  • Política de acesso nas filas, sem deixar de validar no consumidor.

2. Como o SQS entrega

Receber uma mensagem do SQS não a remove. Ela fica invisível por um tempo (o visibility timeout) e, se ninguém chamar DeleteMessage até lá, volta para a fila. Isso protege contra consumidor morto, mas cria a reentrega: a mesma mensagem pode ser processada duas vezes.

3. A inbox

A inbox é uma tabela que lembra quais mensagens já foram tratadas. O ponto importante é que ela é gravada na mesma transação da mudança de saldo:

  1. INSERT ... ON CONFLICT DO NOTHING em inbox_messages.
  2. Linha já existia com o mesmo hash: a mensagem já foi tratada. Nada é refeito.
  3. Linha já existia com outro hash: o produtor reutilizou o messageId para outra coisa. Erro permanente.
  4. Primeira vez: roda o caso de uso (trava a carteira, idempotência, regras, ledger, outbox) e marca completed_at.
  5. Commit. Só então DeleteMessage.

Se o processo morrer depois do commit e antes do delete, a mensagem volta, cai no passo 2 e é removida sem segundo débito. Se morrer antes do commit, o rollback apaga também a linha da inbox, e a reentrega começa do zero.

Por que ON CONFLICT DO NOTHING? Um INSERT comum que bate na chave primária gera erro, e no PostgreSQL um erro aborta a transação inteira. Com DO NOTHING o comando só não insere, e a transação continua usável para consultar a linha existente.

A inbox não é redundante com a idempotência?

Em parte, é. A chave de idempotência já impediria o segundo débito. A inbox acrescenta duas coisas: reconhece a mensagem repetida antes de rodar o caso de uso, e detecta o mesmo messageId com outro corpo, coisa que a chave de idempotência não vê.

E a deduplicação do FIFO?

Ela descarta envios com o mesmo MessageDeduplicationId por 5 minutos. Não cobre reentrega (é a mesma mensagem voltando, não um envio novo), nem um reenvio depois de 5 minutos. A inbox não tem prazo.

O ProcessWagerTransaction.Execute da spec 07 tinha três partes: validar e calcular o hash, abrir a transação (repetindo se perder uma disputa de chave única) e processar. Separei essas partes para o consumidor montar a sua versão:

  • HTTP e SQS calculam o mesmo hash de negócio (spec 07). Se a mesma operação chega pelas duas portas, quem chega depois pega o lock da carteira, encontra a operação gravada e recebe um replay.

6. Ordem por carteira

Um receive traz até 10 mensagens, possivelmente de várias carteiras. O consumidor agrupa por MessageGroupId, roda as carteiras em paralelo (sync.WaitGroup com wg.Go) e as mensagens de cada carteira em sequência.

Se a primeira mensagem de uma carteira falha, as seguintes não podem passar na frente. A AWS documenta que não entrega outra mensagem de um grupo enquanto uma dele está invisível. No teste, o LocalStack entregou. Por isso as seguintes são escondidas pelo mesmo tempo da que falhou e voltam junto com ela. Foi um teste que falhou que mostrou isso.

Spec 12

Reconciliação

O saldo da carteira é guardado numa coluna, e cada movimento também fica no ledger. Se tudo está certo, somar o ledger dá o saldo. A reconciliação faz essa conta sob demanda e avisa quando não bate, sem consertar nada.

1. O que a spec pedia

  • POST /wallets/:walletId/reconciliation, só para o serviço interno.
  • Saldo calculado = créditos − débitos do ledger, incluindo a abertura.
  • difference = armazenado − calculado.
  • Saldo e ledger lidos numa visão consistente.
  • Divergência na resposta, no log e numa métrica. Nunca alterar o saldo.

2. O problema: duas leituras, dois instantes

A reconciliação faz duas consultas: lê o saldo da carteira e soma o ledger. Enquanto isso, apostas continuam chegando. No nível de isolamento padrão do PostgreSQL, READ COMMITTED, cada comando enxerga o que estava confirmado quando ele começou:

  1. Reconciliação lê o saldo: 9904.00.
  2. Uma aposta de 1.00 confirma: saldo 9903.00 e um lançamento novo no ledger.
  3. Reconciliação soma o ledger: já inclui a aposta, dá 9903.00.
  4. Resultado: diferença de 1.00. Uma divergência que não existe.

Isso não é teoria: rodei o teste de concorrência com READ COMMITTED e ele acusou várias divergências falsas de exatamente 1.00, o valor de cada aposta.

3. A solução: REPEATABLE READ

Em REPEATABLE READ, a transação tira uma "foto" do banco na primeira consulta e todas as leituras seguintes enxergam essa mesma foto, mesmo que outros confirmem mudanças no meio.

NívelCada leitura vêUso aqui
READ COMMITTEDO que estava confirmado quando o comando começouPadrão de todas as operações; os locks de carteira cuidam da concorrência
REPEATABLE READO que estava confirmado na primeira consulta da transaçãoReconciliação
SERIALIZABLEComo se as transações rodassem uma de cada vezNão usado
 
func (m *TxManager) WithinSnapshot(ctx context.Context, fn func(ctx context.Context) error) error {
    if inTx(ctx) {
        return errors.New("snapshot requested inside another transaction")
    }
    return m.within(ctx, pgx.TxOptions{IsoLevel: pgx.RepeatableRead, AccessMode: pgx.ReadOnly}, fn)
}
  • READ ONLY: qualquer escrita dentro dela é recusada pelo próprio banco. "Não altera o saldo" deixa de depender só de o código estar certo.
  • Dentro de outra transação seria erro silencioso: o isolamento já foi decidido pela transação de fora. Por isso recusa.
  • Ler em REPEATABLE READ não trava ninguém. O PostgreSQL guarda versões das linhas (MVCC), então as apostas seguem enquanto a reconciliação lê a foto antiga.
Alternativa válida: uma consulta só, juntando carteira e soma do ledger, também enxergaria um único instante, porque um comando sempre vê uma foto só. Escolhi a transação para manter cada repositório com sua consulta, e porque a spec pedia o isolamento explícito.

4. A conta

SELECT COALESCE(SUM(CASE direction WHEN 'CREDIT' THEN amount_minor ELSE -amount_minor END), 0)::bigint,
       count(*)
  FROM wallet_ledger_entries

Spec 13

Observabilidade

Quando algo dá errado em produção, só restam os logs e as métricas. Esta spec faz cada log carregar os identificadores da operação sem que ninguém precise lembrar de passá-los, mede o que o desafio pede e faz o readiness dizer qual dependência caiu.

1. O que a spec pedia

  • Logs JSON com correlationId, messageId, transactionId, walletId, providerId; nada de token ou corpo da operação.
  • Métricas: transações por tipo e status, duplicatas, retries, DLQ, conflitos, atraso da outbox, latência, reconciliação.
  • /health/live e /health/ready (Postgres e SQS).

2. Campos de log que viajam no context

O jeito ingênuo é passar "correlationId", id em cada chamada de log. Alguém sempre esquece. A alternativa é guardar os campos no context.Context da requisição e deixar o handler do slog acrescentá-los sozinho.

func (h *ContextHandler) Handle(ctx context.Context, record slog.Record) error {
    if f, ok := ctx.Value(fieldsKey{}).(*fields); ok {
        record = record.Clone()
        record.AddAttrs(f.snapshot()...)
    }
    return h.next.Handle(ctx, record)
}
  • slog.Handler é a interface que decide o que fazer com cada registro. ContextHandler envolve o handler JSON (padrão decorator): acrescenta os campos e repassa.
  • Por isso todo log precisa usar as variantes com contexto: logger.InfoContext(ctx, ...).
  • WithFields(ctx, ...) cria o conjunto; AddFields(ctx, ...) acrescenta a ele.

Por que um ponteiro mutável?

Contextos em Go são imutáveis: context.WithValue cria um filho, e o pai não vê o que o filho ganhou. O access log é escrito pelo middleware de fora, depois que o handler terminou, mas é o handler que descobre o transactionId. Guardando no contexto um ponteiro para o conjunto de campos, o handler acrescenta e o middleware enxerga. Um sync.Mutex protege o conjunto, porque o context pode ser usado por várias goroutines.

3. O access log

Uma linha por requisição, escrita pelo middleware observeRequests:

{"level":"INFO","msg":"http request","method":"POST","route":"/wagering/transactions","status":200,
 "durationMs":15,"correlationId":"trace-1791996601","clientId":"provider-a","providerId":"provider-a",
 "walletId":"01a13b52-...","transactionId":"01a13b52-..."}
  • Para saber o status, o middleware troca o http.ResponseWriter por um que guarda o código passado em WriteHeader. Isso é embedding: a struct embute a interface original e sobrescreve só um método.
  • Nenhum header e nenhum corpo vão para o log. O teste procura o token, a palavra Bearer, o gameId e o valor da aposta. Registrando os headers de propósito, o teste falhou; com o código certo, passa.

Spec 14

Ciclo de vida e shutdown

Subir só quando tudo de que o serviço depende responde, e descer sem perder nem duplicar trabalho. Grande parte já existia aos pedaços; esta spec junta as peças, corrige a ordem e prova com testes que nada fica para trás.

1. O que a spec pedia

  • Composição com fx.Module, fx.Provide, fx.Invoke; start e stop pelo fx.Lifecycle.
  • Start valida configuração e dependências.
  • Workers com cancelamento, prazo por execução e término observável.
  • Stop: parar a entrada, concluir ou liberar o que está em andamento, fechar dependências por último.

2. Como o Fx ordena start e stop

Cada construtor que precisa de start/stop registra um fx.Hook no fx.Lifecycle. O Fx roda os OnStart na ordem em que foram registrados e os OnStop na ordem inversa. Como um construtor só roda depois das suas dependências, o pool do Postgres sobe antes de quem o usa e desce depois.

Faltava um detalhe: o servidor HTTP subia antes dos workers e, portanto, descia depois deles. Enquanto o consumidor terminava o lote, o HTTP continuava aceitando requisições. A correção foi uma linha: registrar o módulo worker antes do httpapi.

3. Start que falha cedo

É melhor o processo morrer na subida, com uma mensagem clara, do que subir e falhar em toda requisição. Além do ping no banco (spec 05), entraram duas checagens:

  • Filas SQS: GetQueueAttributes nas três filas. Uma URL errada impede a subida.
  • JWKS do Keycloak: busca a lista de chaves uma vez e exige pelo menos uma. Sem isso, o serviço subiria e recusaria todo token.

Se um OnStart falha, o Fx executa o OnStop do que já tinha subido e devolve o erro. Como o HTTP sobe por último, a porta nem chega a abrir; o teste confere isso.

4. A parada em duas fases

O consumidor da spec 11 já tinha a ideia certa; agora ela virou um pacote, lifecycle, usado também pelos dois pollers:

type Loop func(pollCtx, workCtx context.Context)

func Attach(lc fx.Lifecycle, loop Loop)
  1. O stop cancela pollCtx: o loop não começa rodada nova nem busca mensagem nova.
  2. O stop espera a goroutine terminar, até 3s antes do prazo.
  3. Se não terminou, cancela workCtx: o trabalho em andamento é interrompido e devolvido.
  4. O OnStop só retorna quando a goroutine terminou de fato. Se ela ignorar tudo, o stop devolve erro em vez de fingir que acabou.

"Término observável" é isso: um canal done fechado pelo defer da goroutine. Sem ele, o stop retornaria na hora e o processo poderia fechar o pool com uma transação no meio.

go func() {
    defer close(done)
    loop(pollCtx, workCtx)
}()

5. Prazo por rodada

Cada rodada de um poller recebe context.WithTimeout(workCtx, lease). O valor não é arbitrário: a reserva (lease) do worker dura 30s, e uma rodada mais longa que isso poderia continuar trabalhando em algo que outra instância já assumiu.

6. Goroutines que sobram

O goleak compara as goroutines vivas no fim do teste com as que existiam no começo. O teste sobe a aplicação inteira contra Postgres, LocalStack e um JWKS falso, consulta /health/ready e para.

O primeiro achado foi real: o cliente HTTP do SDK da AWS mantém conexões keep-alive, e cada uma tem duas goroutines (persistConn.readLoop e writeLoop). Depois do stop, elas continuavam lá. A correção: o cliente SQS e o verificador de tokens ganharam um http.Transport próprio, e o stop chama CloseIdleConnections. Tirando essa linha, o goleak aponta exatamente essas goroutines.

Por que um transport próprio? O http.DefaultTransport é global. Fechar as conexões dele afetaria qualquer outro código do processo. Com um transport por cliente, cada componente fecha só o que é seu.
